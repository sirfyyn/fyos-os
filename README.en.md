# FYOS — For Your Own Sake

A personal operating system in the browser that is built on an agent of your own and runs entirely on your side: a
desktop shell with windows and apps, an MCP hub that bundles tools and interfaces from plugins, and an agent (a mod of
OpenClaw) that works with these tools and asks before taking heavy steps.

This distribution contains only general-purpose parts. Whatever a particular home, account or person needs comes as a
plugin from a repo of its own.

```text
Plugins (one repo each)  fyos-plugin-…            personal, optional
fyos-os (this repo)      web/  hub/  deploy/  installer/
fyos-agent (foundation)  agent behaviour as an OpenClaw mod
OpenClaw (upstream)      base image by digest
```

## What lives here

| Folder | Contents |
|---|---|
| [`web/`](web/README.md) | Desktop shell (Astro with SolidJS): windows, dock, tiles, menu bar; shows hub apps (`ui://`) without any code of its own |
| [`hub/`](hub/README.md) | MCP hub (Python package `fyos-hub`, module `mcp_hub`): MCP at `/mcp`, REST at `/hub/*`, plugins via entry point |
| [`installer/`](installer/README.md) | Installer with a web assistant, a text interface and a command line; explains every building block with pictures |
| `deploy/compose/` | Single-machine setup with Docker Compose (`docker-compose.yml`, `env.example`, `fyos.yaml`, `hub-config.yaml`) |
| `deploy/k8s/base/` | Kubernetes base installation (Kustomize); an overlay sets images and namespace |
| `tools/sauber.py` | Cleanliness check: no private networks, addresses, secrets or forbidden words in the repo |
| `tools/doku_pruefen.py` | Docs check: links, named paths and fixed sections of the Markdown files match the repo |
| `docs/` | [Architecture](docs/ARCHITEKTUR.md), [Hub contract](docs/HUB-VERTRAG.md), [Extending](docs/ERWEITERN.md) |

The linked READMEs and documents are written in German.

## Getting started

The easy way is the installer. It asks for building blocks (core, agent, plugins), shows what they turn into, and
generates the delivery for Docker Compose or Kubernetes.

```sh
pip install ./installer        # Python 3.11 or newer
fyos-install                   # web assistant in the browser; --tui for the text interface
```

![The installer: choose building blocks, with pictures and what they turn into](installer/docs/screenshots/web-bausteine.png)

All steps with pictures: [`installer/README.md`](installer/README.md).

Without the installer, with Docker Compose:

```sh
cd deploy/compose
cp env.example .env            # enter images, model and agent token
docker compose up -d           # then http://localhost:8080
```

The images are built by the CI of this repo (`<registry>/fyos-os/web`, `<registry>/fyos-os/hub`) and by that of
`fyos-agent` (`<registry>/fyos-agent/openclaw`). The defaults point to the example address `registry.example.com`, which
can never be resolved: without a registry of your own, startup fails visibly instead of pulling foreign images. The
installer is pointed at your own registry with `FYOS_REGISTRY=<host>/<owner>`.

Any OpenAI-compatible provider serves as the model (for example a llama.cpp server, Ollama or vLLM), locally or on your
own network.

**The first chat.** The agent window shows the interface of the OpenClaw gateway. When opened for the first time, it asks
for the gateway token (`FYOS_AGENT_TOKEN` from `.env`, in Kubernetes the secret `fyos-agent-gateway`); the browser
remembers it. After that, every new browser needs to be approved once as a device, because the gateway sees it through
the shell as a remote client:

```sh
docker compose exec agent openclaw devices list              # Kubernetes: kubectl exec agent-0 -- openclaw devices list
docker compose exec agent openclaw devices approve <requestId>
```

Over plain http this only works on `localhost`. On a network the shell needs https, because the browser creates the device
identity only in a secure context; otherwise the gateway reports "control ui requires device identity".

## Extending

A plugin is a Python package with the entry point `mcp_hub.plugins`. It can bring tools, an interface, skills for the
agent and an entry in the installer catalog. The starting point is the repo `fyos-plugin-vorlage`; the complete guide with
examples is in [`docs/ERWEITERN.md`](docs/ERWEITERN.md): hub plugin, app, skills, agent behaviour, shell, catalog,
companion services, testing and delivery.

**Packages with uv, your own index first.** FYOS installs plugin packages with [uv](https://docs.astral.sh/uv/) instead of
pip: in the hub image, in the Dockerfile generated by the installer and in the sample plugin. If the plugins live in an
index of your own, its address goes before PyPI via `--index` (as the build argument `FYOS_INDEX_URL`; the installer reads
it from `FYOS_PAKETINDEX`). In addition, `--index-strategy first-index` is set explicitly in the command: uv takes a
package only from the first index that carries it. A package of the same name on PyPI therefore cannot displace a plugin
from your own index (dependency confusion); with `pip --extra-index-url` it could, because pip takes the highest version
from all indexes. The version of uv is pinned in the Dockerfiles. More in [`docs/ERWEITERN.md`](docs/ERWEITERN.md),
section 10.3.

## Developing

```sh
python3 tools/sauber.py .                                         # must be silent
python3 tools/doku_pruefen.py                                     # docs match the repo
pip install -e "hub[test]" && python -m pytest hub/tests -q
pip install -e "installer[test]" && python -m pytest installer/tests -q
cd web && npm ci && npx vitest run && npx astro build
```

The commands for developing and testing this repo use pip because it is available everywhere; with `uv pip install` they
work the same.

The CI (`.gitea/workflows/ci.yml`) checks every push the same way. On `main` it uploads `fyos-hub` as a development build
(`X.Y.Z.devN`) to the package index of the Git server and builds the images `web` and `hub` with the tags `main` and
commit.

On GitHub the same checks run as `.github/workflows/tests.yml`, plus a secret scan with gitleaks. On a `v*` tag,
`.github/workflows/pypi.yml` publishes the packages `fyos-hub` and `fyos-installer` to PyPI (Trusted Publishing, no
stored token) and `.github/workflows/bilder.yml` pushes the images to ghcr.io.

The CI also runs the docs check every night and on demand (`.gitea/workflows/doku-nachts.yml`). It checks all Markdown
files: links and anchors, paths in code snippets (`web/src/lib/hub.ts`) and the fixed sections of the READMEs. What the
docs name but what does not live in this repo (files of `fyos-agent` or from plugin repos, examples, files that only come
into being in operation) is listed with a reason in `.doku/ausserhalb.txt`.
